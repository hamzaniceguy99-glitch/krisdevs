Program 01 · Documented as built

Custom software development

Documentation written at the end of a project is documentation written badly, from memory, under time pressure, by someone already thinking about the next thing. So it is delivered as the work proceeds and it forms part of each milestone. The test is simple and we apply it honestly: could a competent developer who has never met us pick this up?

Program 02 · Fewer moving parts

Systems integration and automation

Before automating a process we ask whether it should exist, because automating an unnecessary step makes it permanent and harder to question later. We also prefer the smaller integration that can be understood to the elegant one that cannot: every connection between two systems is something that will break at some point, usually when nobody remembers how it worked.

Program 03 · Before you commit

Technical second opinions

A short review before signing is the cheapest technical work a business ever buys. We read the codebase or the proposal and report plainly: what is solid, what is risky, what is missing, and whether the price bears any relation to the work. If the answer is that the existing supplier is doing a decent job, that is the report you get.

Program 04 · Written for your sake

Continuity and handover

This is the service that argues against our own indispensability, which is exactly why it is here. Accounts and domains in your name, administrative access held by you, source code deposited with a third party if you want it, and a named substitute contractor for longer engagements. A supplier who has not done this is relying on your inability to leave.
